- **核心问题**：模型自生成问题和答案用于微调时，源数据中的指令污染会怎样破坏训练信号？
- **方法概述**：论文研究指令注入对问题生成的影响，并提出 Clustered Conformity Filtering 过滤异常/低质量样本。
- **技术创新**：把 prompt injection 风险从用户交互扩展到训练数据生成链路。
- **实验设置/主要结果**：摘要报告注入简单指令后，有用问题比例从 88% 降到 13%；过滤方法可缓解。
- **局限**：实际 web 语料污染更复杂，过滤可能删除少数但重要的长尾样本。
- **代码/数据开放情况**：摘要页未明显显示仓库入口，需后续核验。
- **是否值得精读**：A-。做 RAG、合成数据、蒸馏、自训练的团队应读。
- **研究启发**：数据生成 agent 也需要安全边界和审计，而不只是线上 chatbot 需要。
- **复现实验切入点**：在自己的文档 QA 生成流程中加入 20 种恶意/无关指令，测量问题质量、答案覆盖和训练后性能。

- **获客**：从法务、HR、采购、信息安全和内审团队切入。
- **商业化**：按团队席位、政策数量、审计量或私有部署收费。
- **风险**：合规解释责任高，必须提供人工复核，不可自称法律意见。
- **7 天验证动作**：选一家虚构公司，写 30 条政策和 100 个 agent 输出样例，做一个可视化合规报告 demo。

- **技术门槛**：医疗流程建模、工具仿真、隐私合规、专家标注。
- **商业化**：向医疗 AI 公司、医院创新中心、保险科技团队提供评测服务。
- **风险**：不能进入诊断建议灰区，必须定位为工程评测与流程安全。
- **7 天验证动作**：复刻 20 个非诊断流程任务，如随访安排、用药清单核对、资料缺失提醒，找 2 名医学背景用户评估错误分类。

## 12. 深度技术解读

### 12.1 今日模型/系统：Xiaomi-GUI-0 与真实设备 GUI agent

**背景**：传统 GUI agent 多基于静态截图、网页环境或模拟器任务。真实手机环境更复杂：应用状态会变化，权限弹窗会出现，网络会波动，UI 版本不同，用户数据敏感，错误点击可能造成真实后果。Xiaomi-GUI-0 的价值在于把研究对象推向真实设备交互，而不是停留在截图理解。

**架构/原理**：一个 GUI agent 通常需要四层：观测层读取截图、UI tree、OCR 和系统状态；规划层把用户任务拆成子目标；动作层生成点击、滑动、输入、返回、等待等操作；验证层判断当前状态是否接近目标并决定是否重试或回滚。真实设备闭环数据可以让模型学习“动作后状态如何变化”，这比只看静态图片更接近具身智能。

**数学与建模视角**：GUI 操作可视为部分可观测马尔可夫决策过程。状态不是完全可见，动作结果有不确定性，奖励通常稀疏。模型需要在历史观测、当前 UI 和任务文本之间建立策略。关键难点是 credit assignment：失败可能来自识别错误、任务分解错误、动作坐标错误、权限限制或外部网络状态。

**工程实现**：最小系统可用 Android emulator 或真实设备，记录截图、accessibility tree、动作和结果。训练时可混合 supervised behavior cloning、trajectory ranking 和失败恢复样本。部署时必须有权限白名单、危险动作确认、日志、超时、人工接管和隐私脱敏。

**优点**：更接近用户真实场景；可连接手机厂商生态；适合自动化测试、个人助理、客服流程、无障碍辅助。

**缺点**：数据采集成本高；隐私敏感；跨地区 app 差异大；真实执行风险高；benchmark 容易被应用版本变化破坏。

**科研启示**：GUI agent 需要从“视觉问答”转向“状态转移建模和执行安全”。未来论文应报告失败恢复、权限处理和用户数据保护，而不只报告任务成功率。

**产业应用**：手机系统助手、企业移动 RPA、自动化测试、客服工单处理、个人效率工具。

**未来 1-3 年影响**：如果 OS 厂商开放安全执行接口，GUI agent 会成为移动端 AI 入口；如果权限和隐私问题解决不好，它会被限制在低风险自动化和测试场景。

### 12.2 今日算法思想：verifier-guided repair for coding agents

**背景**：LLM 写代码的问题不是不会生成，而是生成内容缺少可验证保证。单元测试只能覆盖有限样例，静态分析只能发现某些错误，形式化验证则要求程序满足规格。

**核心思想**：让模型生成代码后，把代码交给 verifier。verifier 返回证明失败、类型错误、不变式不足或反例。agent 再根据反馈修改规格、循环不变式或实现，直到通过验证或达到预算上限。

**数学原理**：形式化验证通常把程序正确性转化为逻辑公式。以循环为例，需要找到不变式，使得初始化、保持性和终止后条件都可证明。SMT solver 负责判定约束是否可满足。LLM 的作用不是替代 solver，而是提出候选实现、候选不变式和修复解释。

**工程实现**：一个实用 pipeline 包括：规格输入、代码生成、Dafny/Lean/Coq 检查、错误解析、反例摘要、修复策略选择、预算控制和最终报告。关键是把 verifier 的低层错误转成模型可操作的反馈。

**优点**：比单测更强；适合小而关键的算法模块；可生成审计证据。

**缺点**：规格编写成本高；证明搜索复杂；大型系统难以端到端形式化；模型可能反复修改规格逃避证明。

**科研启示**：未来 AI coding benchmark 应该增加“规格保持”和“证明义务”维度，而不是只看 pass@k。

**产业应用**：智能合约、金融风控算法、权限系统、医疗设备软件、安全协议、编译器优化。

**未来 1-3 年影响**：AI coding 工具会分层：普通业务代码用测试和 review，高风险模块用 verifier 和 proof assistant 约束。

### 12.3 今日前沿技术概念：policy-as-code for agents

**背景**：企业政策通常是自然语言文档，agent 执行时却需要机器可判定的约束。比如“客户数据不得发送给外部供应商，除非有 DPA 且经过审批”包含对象、条件、例外、流程和责任主体。

**核心思想**：把组织政策转成可测试规则、例外条件、风险等级和证据要求。agent 每次计划动作或生成输出时，policy engine 先判断是否允许、需要审批、需要脱敏，还是必须拒绝。

**数学与表示**：可使用逻辑规则、决策表、知识图谱、约束求解或 neuro-symbolic 方法。LLM 负责理解上下文和抽取事实，符号层负责稳定执行规则。难点是事实抽取不确定、规则冲突和政策版本变化。

**工程实现**：最小系统包含政策解析、规则库、测试样例、上下文事实抽取、合规判定、解释生成、人工复核和审计日志。每条政策都应有正例、反例和边界例。

**优点**：可审计、可回归测试、便于合规团队参与。

**缺点**：政策解释复杂，规则维护成本高；过度形式化会漏掉语境；LLM 抽取事实会出错。

**科研启示**：agent safety 不应只有通用 refusal benchmark，还需要行业/组织级 policy benchmark。

**产业应用**：企业 AI 助理、GovTech、金融投研 agent、医疗流程助手、人力资源自动化、采购审批。

**未来 1-3 年影响**：成熟企业 agent 平台会把 policy engine、权限系统、日志和 eval 作为标配，否则难以进入高风险流程。
