今天重点解释一个概念：agent 技能供应链。你可以把它理解为 agent 的“包管理系统”。过去我们做 agent，常常只有模型、工具、RAG 文档和 prompt。模型负责生成，工具负责执行，RAG 负责查资料，prompt 负责约束行为。但真正进入企业场景后，agent 还需要很多操作性知识：怎么安全修改 Kubernetes 配置，怎么处理某个数据库迁移，怎么按公司流程生成采购单，怎么复现实验，怎么检查日志。这些知识如果只是散落在文档里，模型很难稳定使用；如果只是写在 prompt 里，又难维护、难审计、难更新。

技能供应链的想法是，把这些操作性知识做成结构化技能。每个技能都应该说明适用场景、输入、输出、步骤、风险、权限、测试样例、来源和版本。来源很重要，因为没有来源的技能就像没有来源的软件包，可能过时、错误、带有危险操作，甚至被恶意投毒。运行时 agent 检索技能，不应该只按语义相似度，还应该按来源可信度、更新时间、权限等级和任务类型过滤。

这个概念的工程落地并不一定复杂。最小版本可以是一套 SQLite 或向量检索库，加上技能 schema、来源链接、风险标签、版本号和测试用例。更成熟的版本会像企业软件供应链一样，有审核、签名、弃用、权限分级和运行日志。它的意义在于，未来 agent 的能力差异不只来自模型大小，也来自谁有更可靠、更干净、更可审计的技能库。

今天给程序员和 AI 工程师的行动建议很具体：给你的 AI workflow 增加中间状态记录。不要只保存最终答案。至少记录任务目标、输入材料、检索来源、调用工具、使用技能、生成文件、测试输出、失败样本和人工修改点。如果你做多模态系统，还要记录 caption、OCR 和视觉摘要的来源与置信度。如果你做科学建模，要记录模型除了误差之外是否满足物理断言。如果你做 agent，要记录每个技能来自哪里、有没有测试、有没有权限风险。

对求职者，今天的建议是把“会使用 AI 工具”改成“能构建可验证的 AI 工作流”。例如你可以展示：你如何让 agent 完成某类任务，如何记录 trace，如何设计评测集，如何发现失败样本，如何降低误报，如何用测试或业务指标验证结果。相比说自己熟悉某个模型或工具，这更能证明工程判断力。

对创业者，今天值得验证三个方向。第一个是 agent skill registry，帮企业管理可复用技能和安全权限。第二个是科学机器学习物理断言测试，帮助研究和工程团队筛掉低误差但违反物理规律的模型。第三个是多模态流水线中间状态审计，检测错误 caption、OCR 或视觉摘要如何影响后续决策。这些方向都不只是概念，有明确用户痛点，也可以在一周内做小 demo。
